ElectraVote — How to Build and Run
================================

ElectraVote is an educational/demo voting application. It is not certified or
approved for legally binding public elections. The application uses a C++17
backend, a vanilla HTML/CSS/JavaScript frontend, SQLite persistence, and
libsodium for password hashing and secure random generation.

Requirements
------------

- Linux or WSL with g++ and make
- C++17 support
- Runtime libraries available at the paths configured in Makefile:
  libsodium.so.23 and libsqlite3.so.0
- A modern web browser
- bash and curl to run the integration smoke tests

Build and start
---------------

1. Open a terminal in the repository directory (the directory containing
   Makefile and start.sh). Build the application:

    make

   A successful build creates the voting_server executable. The build links
   the installed SQLite and libsodium runtime libraries configured in Makefile.

2. Start the server:

    ./start.sh

   The script builds again if necessary, creates the default data directory,
   and starts the HTTP server on port 8080. Keep this terminal open while
   using the app. Startup output identifies the port and database path.

3. Open this address in a browser on the same computer:

    http://localhost:8080

   To use another port, pass it to the script and use that same port in the
   browser. For example:

    ./start.sh 9000

   Then visit http://localhost:9000. Press Ctrl+C in the server terminal to
   stop the application. Restarting with the same data directory keeps the
   accounts, organizations, elections, and ballots in the SQLite database.

You can also run the binary directly after building. These arguments select
the port, frontend folder, and data folder:

    ./voting_server 8080 web data

When using environment variables with start.sh, OV_PORT sets the default
port; an explicit positional port such as ./start.sh 9000 takes precedence.

Initial administrator account
------------------------------

There is no default admin/admin123 account. On a fresh data directory, the
server creates the username "admin". If OV_INITIAL_ADMIN_PASSWORD is unset,
the server generates a random password and prints it once in the server
terminal. Save it securely at that time; the application does not write this
password to a file or provide web-based password recovery.

To choose the initial password explicitly, set the environment variable when
starting the server. For example:

    OV_INITIAL_ADMIN_PASSWORD='choose-a-unique-password' ./start.sh

Choose a password of at least 8 characters. Do not put a real password into
shared shell history, screenshots, logs, or this document. The initial admin
is created only when the database has no active platform administrator.

If the database contains a legacy admin account, including one imported from
admins.csv, the server keeps that account and does not generate another admin
password. In that case use the legacy account password. If it is unavailable,
use the local recovery command below; OV_INITIAL_ADMIN_PASSWORD does not
replace the password of an account that already exists.

Recover an administrator password
---------------------------------

1. Stop the running server with Ctrl+C. Run this local recovery command only
   from a trusted computer with access to the project files and database.
2. From the repository directory, run:

       ./start.sh --reset-admin-password

   For an admin account with a different username, add it after the command:

       ./start.sh --reset-admin-password admin_name

3. Enter a new password of 8-256 characters twice when prompted. The terminal
   does not display the password as you type. The command updates only that
   administrator's password hash, leaves election and ballot data untouched,
   and revokes existing sessions for that account.
4. Start the server normally with ./start.sh and log in with the same username
   and the new password.

The command uses the database selected by OV_DB_FILE or, if that is unset,
OV_DATA_DIR/openvote.db (default data/openvote.db). If you normally start with
a custom data directory, use the same setting for recovery, for example:

    OV_DATA_DIR=./demo-data ./start.sh --reset-admin-password

Check the data path printed at server startup before running recovery. If the
database file does not exist or the username is not an enabled platform admin,
the command exits without creating a database or changing data.

Data and configuration
----------------------

By default, the application stores its SQLite database at
data/openvote.db. The server creates the data directory if needed. Existing
legacy CSV files in that directory may be imported once into a fresh database;
the CSV files are left in place. Historical votes imported from the legacy
format remain identity-linked and are not anonymous.

Development deployment boundary
-------------------------------

The built-in HTTP server is a development server. It binds to 0.0.0.0 and
does not provide TLS, trusted-proxy client-IP handling, durable rate limiting,
or production-grade operational controls. Do not expose its port directly to
the internet. A production architecture would need an independently reviewed
HTTPS reverse proxy, with the application port restricted by a host/network
firewall to that proxy. Set OV_SECURE_COOKIES=1 only when HTTPS is correctly
terminated and the browser reaches the app over HTTPS.

The application's failed-login throttling is in memory and resets on restart.
It cannot coordinate across multiple server processes, and requests forwarded
by a proxy appear to come from that proxy's IP. Add reviewed gateway-side
throttling and do not treat the application's limiter as a deployment control.

The SQLite database uses WAL mode. Stop the server before making a simple
filesystem backup, preserve the database and any SQLite sidecar files together,
and keep the backup access-restricted. Do not remove WAL/SHM files by hand.
For live backups, use SQLite's supported backup API; the application does not
currently provide a backup command. Test restoration against a separate data
directory before relying on a backup.

Audit events include account names and timestamps. Restrict access to the
database and server logs, rotate and retain them under a written policy, and
never collect passwords, session tokens, or ballot choices in operational
logs. Independent security, privacy, accessibility, legal, and operational
reviews are required before any real election use; this guide is not a
production deployment procedure.

If you are trying the application for the first time and want to keep its
database separate from any existing project data, run it with a new data path:

    OV_DATA_DIR=./demo-data ./start.sh

This creates or uses ./demo-data/openvote.db. Keep that directory to preserve
the demo state. Do not point a fresh database at a folder containing legacy
CSV files unless you intend to import those records. The one-time import does
not delete the CSV files, but imported historical data may include
identity-linked ballots. Back up a database before moving or changing data
directories.

Configuration can be provided through environment variables:

- OV_PORT: listening port (default 8080)
- OV_WEB_DIR: static frontend directory (default web)
- OV_DATA_DIR: data directory (default data)
- OV_DB_FILE: SQLite database path (default <data directory>/openvote.db)
- OV_SESSION_HOURS: session lifetime (default 168 hours)
- OV_SECURE_COOKIES: set to 1 when HTTPS is correctly terminated by a trusted
  reverse proxy; default 0 for local HTTP development
- OV_INITIAL_ADMIN_PASSWORD: initial admin password, as described above

Positional arguments to the binary remain supported:

    ./voting_server [port] [web_dir] [data_dir]

Common commands
---------------

    make              Build voting_server
    make run          Build and run on port 8080
    make run-port PORT=9000
                      Build and run on the selected port
    make test         Run integration smoke tests (bash + curl required)
    make clean        Remove compiled object files and voting_server

First login and administrator setup
-----------------------------------

1. On the first start of a new database, note the initial admin password
   printed in the server terminal (unless you set OV_INITIAL_ADMIN_PASSWORD).
   The account name is admin. The generated password is displayed once; save
   it somewhere private before closing the terminal.
2. In the browser, choose Log in and enter username admin and that password.
   The session is held in a server-managed HttpOnly cookie; the frontend does
   not store the password.
3. Open Administration. A platform administrator can create an organization
   by entering its name and unique slug. This gives the application a place to
   scope its elections, users, and observer access.
4. In the Users area, create accounts as needed. Choose the account role and
   organization. Organization administrators can administer elections within
   their organization; observers have read-only access; voter accounts can
   participate only when eligible for an election.

Create and prepare an election
------------------------------

1. In Administration, create a new election and select its organization. An
   organization administrator creates elections in their own organization.
   New elections start in Draft.
2. Open the election's management page. In Configuration, set the name and
   description, and optionally set the start/end values in ISO UTC format.
   Draft elections are the only elections whose configuration can be edited.
   Leave live totals disabled unless the election rules intentionally permit
   results to be shown while voting is open.
3. In Candidates, add every candidate or ballot option and its shared
   information fields. Review the list before opening the election; the ballot
   options cannot be changed after the election leaves Draft.
4. In Voter list, add the username of each account allowed to vote. Voters
   must already have accounts. Self-registration creates a voter account, but
   does not automatically make that user eligible for a particular election.
5. Confirm the election description, options, voter list, and published rules
   before choosing Open election. Opening the election allows eligible voters
   to submit one ballot and locks its configuration.

Voter steps
-----------

1. Choose Register to create a voter account with a username, display name,
   and password of at least 8 characters. If an administrator already created
   the account for you, use Log in instead.
2. Ask the election administrator to add your username to the election's
   voter list. If the election is not listed after login, it may not yet be
   open or you may not be eligible for it.
3. Log in and open Elections. Select an election marked Open to view its
   description and ballot options.
4. Select one option. No option is selected automatically. Choose Cast vote
   and confirm the selection in the browser confirmation prompt. The server
   records the ballot once; it cannot be changed or submitted again by that
   account for that election.
5. The election page confirms whether your ballot was recorded. It does not
   reveal the stored ballot to administrators. Results are unavailable until
   publication unless an administrator deliberately enabled live totals.
6. Choose Log out when finished, especially on a shared computer.

Close and publish results
-------------------------

1. When voting ends, an administrator opens the election management page and
   chooses Close election. No further ballots are accepted after closing.
2. Review the election and choose Publish results to run the tally and make
   the results public. The server checks the tally integrity before
   publication. Published results can be viewed from the results page and
   downloaded as a CSV report.
3. An administrator may then archive the published election. Archived
   elections remain historical records and are not open for voting.

An observer can log in and use Observer view to inspect elections and the
available audit trail for their organization. Observer accounts cannot change
election configuration or cast ballots.

The available actions depend on the account role, organization, eligibility,
and election status. A hidden or disabled frontend button is not the security
boundary; protected operations are checked by the server.

Troubleshooting
---------------

"Address already in use": start on another port, for example ./start.sh 9000.

"g++: command not found" or "make: command not found": install the compiler
and build tools using the package manager for your Linux distribution.

Missing libsodium or SQLite runtime library: install the matching runtime
packages or update the library paths in Makefile for your system.

Browser cannot connect: confirm the server is running, use the same port shown
in its startup output, and check local firewall settings.

Security and privacy limits
---------------------------

This is an educational/demo application, not production election software.
Its database separates participation records from ballot choices, but this
does not provide cryptographic anonymity or prevent timing and operational
metadata from linking a voter to a ballot. The development server uses plain
HTTP unless protected by a correctly configured HTTPS reverse proxy. Do not
use it for a legally binding election or claim certification, anonymity, or
end-to-end verifiability without independent review and evidence.
